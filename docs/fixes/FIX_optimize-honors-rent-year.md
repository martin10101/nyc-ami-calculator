# FIX: "Find Optimal Scenarios" honors the rent-roll year

**Branch:** `fix/optimize-honors-rent-year`
**Cut from:** `feature/excel-agent-foundation` @ `31a7ac2`
**Date:** 2026-06-10
**Risk:** Low — Excel adds one payload field; the server switches to the same per-request resolver Manual Calculate has used for weeks; payloads without the field behave exactly as before (regression-tested).

## Symptom

The client built AMI options manually using the 2026 rent roll and reported that all her options "generated a greater income than any of the options generated by the optix." Investigation (Building D, 35-19 Steinway) proved every rent in her file matched the 2026 table to the dollar, while the optimizer's scenario blocks matched the **2025** table to the dollar. She was comparing 2026-priced manual numbers to 2025-priced program output — the program displayed $43,831 when its true 2026 answer is $45,376/mo, which beats her best ($44,933) by $443/mo.

## Root cause

The rent roll lives in three paths and only two of them honored the Excel year dropdown:

| Path | Where rents compute | Honors year dropdown? |
|---|---|---|
| Live AMI-cell edits (Manual Working Copy) | Locally in Excel from the local RentCalculator file | ✓ |
| Manual Calculate button (`/api/evaluate`) | Server, **with `rent_roll_year` sent per request** | ✓ |
| Find Optimal Scenarios (`/api/optimize`) | Server, **no year field in the payload at all** | ✗ |

`BuildAPIPayloadV2` (the optimize payload builder) never included `rent_roll_year`, and the optimize route used `_get_active_rent_calculator_path()` — the server-global "active" selection. That selection is a file on Render's **ephemeral** filesystem (no persistent disk — verified via the Render API), so **every deploy resets it to the hard-coded 2025 default**. With deploys happening near-daily, the optimizer was effectively pinned to 2025 forever, regardless of the dropdown. The mixed result: manual blocks in the workbook showed dropdown-year rents while scenario blocks showed 2025 rents, with nothing on screen revealing the difference.

## Fix

### 1. Excel sends the year ([AMI_Optix_API.bas](excel-addin/src/AMI_Optix_API.bas), `BuildAPIPayloadV2`)

Added `"rent_roll_year": <dropdown year>` to the optimize payload — the same `GetSelectedRentRollYearSetting()` pattern `BuildEvaluatePayloadV2` already uses. All optimize callers (Main, Automation, legacy) funnel through this one builder.

### 2. Server honors it ([app.py](app.py), optimize route)

Replaced `_get_active_rent_calculator_path()` with `_resolve_rent_calculator_for_request(data)` — the existing, battle-tested resolver `/api/evaluate` uses. Resolution order: explicit `calculator_id` → `rent_roll_year` → server-global active → 2025 default. Payloads without a year (older add-ins) hit the same fallback chain as before — behavior unchanged.

Pre-solver messages are collected in `rent_resolution_notes` and merged once `notes` exists (the old code had a latent `UnboundLocalError` on the load-failure path; fixed as a side effect).

Response now carries `rent_roll_year_used`, `rent_calculator_filename`, `rent_schedule_source`, and a visible note: *"Rents priced on the 2026 rent roll."*

### 3. Year guardrail on the results sheet ([AMI_Optix_ResultsWriter.bas](excel-addin/src/AMI_Optix_ResultsWriter.bas))

`WriteManualScenarioBlockFromResult` prints **"Rent Roll Year: NNNN"** directly under the "AMI OPTIMIZATION RESULTS" title, from the server's `rent_roll_year_used`. If an older server omits the field, it falls back to the local dropdown year labeled "(local)". A year mismatch can never be invisible again.

## Verified

- [tests/test_optimize_rent_year.py](tests/test_optimize_rent_year.py) — 5 new tests: 2024/2025/2026 each price a 40% 2BR at its known net ($1,099/$1,069/$1,131) with `rent_roll_year_used` echoed and the note present; no-year payload preserves legacy default behavior (2025); unknown year (2031) falls back to default **with a warning note**.
- Full suite: **75 passed** (70 existing + 5 new), zero regressions.
- End-to-end Building D probe (real client workbook, 25-unit pool):
  - `rent_roll_year: 2025` → absolute_best **$43,831/mo** — byte-identical to the output saved in the client's workbook (legacy equivalence).
  - `rent_roll_year: 2026` → absolute_best **$45,376/mo** — the correct 2026 answer, beating the client's best manual option ($44,933) by $443/mo.

## Deploy

- Render auto-deploys the server side from `feature/excel-agent-foundation`.
- **Client PCs need the standard `.xlam` refresh** (VBA changed): both the year field and the "Rent Roll Year" header line live in the add-in.
- Until a PC refreshes its add-in, it keeps working exactly as before (no year sent → server default), so the rollout has no ordering constraints.

## Out of scope

- Server-side persistent disk / durable "active calculator" state (made irrelevant for optimize by per-request resolution).
- Low-40 ladder, Ctrl+Z fix, solver logic — untouched.
